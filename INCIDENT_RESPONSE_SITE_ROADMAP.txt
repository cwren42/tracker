PROJECT OVERVIEW
================================================================================
Build a comprehensive security incident response portal that integrates with
existing SOC2 compliance tracking system. The portal will manage the complete
incident lifecycle from detection through resolution, with automated workflows
based on SOC2 policies and procedures.

Current Asset Tracker:        tracker.corp.cirque.com (port 8000)
New Incident Portal:          incident.corp.cirque.com (port 8001)
Integration:                  Shared database, unified authentication


CORE FEATURES & FUNCTIONALITY
================================================================================

1. INCIDENT INTAKE & TRIAGE
   -------------------------
   ☐ Multi-channel incident reporting
     - Web form (internal employees)
     - Email monitoring (security@cirque.com forwarding)
     - API endpoint (automated alert integration from Azure Sentinel)
     - Mobile-responsive reporting interface
   
   ☐ Automated severity classification
     - AI-assisted severity scoring based on keywords/indicators
     - Manual override with justification
     - Automatic escalation based on severity (from IR Plan)
     - Real-time alerts to IR Team members
   
   ☐ Incident categorization
     - 11 categories from IR Plan: Malware, Phishing, Unauthorized Access,
       Data Breach, DoS/DDoS, Lost/Stolen Device, Physical Security,
       Insider Threat, Vendor Incident, Web Attack, Account Compromise
     - Auto-tagging based on description keywords
     - Custom tags for tracking

2. AUTOMATED TICKET ROUTING & ASSIGNMENT
   ---------------------------------------
   ☐ Smart assignment based on:
     - Incident type → responsible team member (Security Analyst, IT Ops, etc.)
     - Severity level → automatic IR Team activation
     - Current workload balancing
     - On-call schedule integration
   
   ☐ Escalation matrix automation
     - Sev 1: CTO/CEO notification within 1 hour (automatic email/SMS)
     - Sev 2: CTO/IT Manager immediate notification
     - Sev 3: IT Manager notification within 4 hours
     - Sev 4: IT Security handles, weekly summary
   
   ☐ On-call schedule management
     - Weekly on-call rotation (Security Analyst, IT Ops)
     - Automatic failover to backup responder if no acknowledgment
     - Integration with phone/SMS for after-hours incidents

3. INCIDENT RESPONSE WORKFLOW ENGINE
   -----------------------------------
   ☐ Guided playbook execution
     - 4 detailed playbooks from IR Plan:
       * Ransomware playbook (14 steps with checklist)
       * Phishing playbook (10 steps with checklist)
       * Data Breach playbook (12 steps with checklist)
       * Lost/Stolen Device playbook (8 steps with checklist)
     - Step-by-step guided interface with action verification
     - Automated containment actions where possible
   
   ☐ NIST SP 800-61 phase tracking
     - Phase 1: Preparation (pre-incident readiness check)
     - Phase 2: Detection & Analysis (evidence collection)
     - Phase 3: Containment, Eradication, Recovery (action tracking)
     - Phase 4: Post-Incident (lessons learned, reporting)
     - Visual progress indicator showing current phase
   
   ☐ Timeline documentation (automatic)
     - All actions auto-logged with timestamp
     - User actions (account disabled, password reset, etc.)
     - System events (alerts triggered, sessions terminated, etc.)
     - Communications (emails sent, calls made, meetings held)
     - Evidence collected (logs, screenshots, forensic data)
   
   ☐ Containment action tracking
     - Pre-built containment action library:
       * Disable user account (Azure AD API integration)
       * Revoke user sessions (Azure AD API)
       * Reset password (Azure AD API)
       * Block IP address (Azure Firewall API)
       * Quarantine email (Microsoft Defender API)
       * Remote wipe device (Intune MDM API)
       * Block domain (Microsoft Defender for Office 365 API)
     - One-click execution with confirmation
     - Automatic documentation in incident timeline
     - Rollback capability for reversible actions

4. FORENSICS & EVIDENCE COLLECTION
   ---------------------------------
   ☐ Integrated log collection
     - Azure AD sign-in logs (API pull for affected user)
     - Exchange Online mailbox audit logs (API pull)
     - Azure Firewall network traffic logs (API pull)
     - Microsoft Defender for Endpoint scan results (API pull)
     - Automatic export and attachment to incident ticket
   
   ☐ Evidence upload and management
     - Drag-and-drop file upload (screenshots, email samples, etc.)
     - Chain of custody tracking (who uploaded, when, why)
     - Evidence tagging and categorization
     - Secure storage with access logging
   
   ☐ Impact assessment calculator
     - Systems affected counter
     - Data exposure calculator (PII records, confidential docs, etc.)
     - Financial impact estimator (labor hours, external costs, downtime)
     - Regulatory notification requirement checker (GDPR, CCPA, PCI, HIPAA)
   
   ☐ Root cause analysis framework
     - Guided "5 Whys" template
     - Fishbone diagram builder (Ishikawa)
     - Technical gap identification
     - Human/process gap identification
     - Corrective action recommendation engine

TECHNICAL ARCHITECTURE
================================================================================

Technology Stack:
-----------------
Backend:           Python 3.11 + Flask 3.0
Database:          SQLite (shared with asset tracker, new tables)
Frontend:          HTML5, Bootstrap 5, JavaScript/jQuery
Charts:            Chart.js for dashboards
Real-time:         Flask-SocketIO for live updates
Authentication:    Shared session with asset tracker (existing users)
API Integration:   Microsoft Graph API, Azure REST APIs
Task Queue:        Celery + Redis (for async API calls, email sending)
Web Server:        Gunicorn (3 workers on port 8001)
Reverse Proxy:     Nginx (subdomain routing)
Deployment:        Same server as asset tracker (/var/www/incident/)

Database Schema (New Tables):
------------------------------

TABLE: incidents
  - id (PRIMARY KEY)
  - incident_number (INC-YYYY-NNNNN, auto-generated, unique)
  - title (short description)
  - description (detailed description)
  - severity (1=Critical, 2=High, 3=Medium, 4=Low)
  - category (Malware, Phishing, Data Breach, etc.)
  - status (New, Investigating, Contained, Eradicated, Recovered, Closed)
  - reported_by (user ID, FK to users table)
  - reported_date (timestamp)
  - assigned_to (user ID, FK to users table)
  - ir_manager (user ID, FK to users table)
  - detected_date (when incident actually occurred)
  - contained_date (when containment completed)
  - resolved_date (when fully resolved)
  - closed_date (when ticket closed)
  - nist_phase (Preparation, Detection, Containment, Post-Incident)
  - playbook_used (Ransomware, Phishing, Data Breach, Lost/Stolen, Custom, None)
  - root_cause (text field for analysis)
  - impact_systems_count (integer)
  - impact_data_exposed (text field describing data)
  - impact_pii_count (integer - number of PII records)
  - impact_financial_cost (decimal)
  - regulatory_notification_required (boolean)
  - regulatory_notifications_sent (text field with dates)
  - tags (JSON array of custom tags)
  - created_at (timestamp)
  - updated_at (timestamp)

TABLE: incident_timeline
  - id (PRIMARY KEY)
  - incident_id (FK to incidents)
  - timestamp (when event occurred)
  - event_type (Detection, Action, Communication, Evidence, StatusChange, etc.)
  - actor (who performed action - user ID or "System" for automated)
  - description (what happened)
  - details (JSON field for structured data)
  - created_at (timestamp)

TABLE: incident_evidence
  - id (PRIMARY KEY)
  - incident_id (FK to incidents)
  - evidence_type (Log, Screenshot, Email, Document, Forensic, Other)
  - file_name (original filename)
  - file_path (storage path on server)
  - file_size (bytes)
  - uploaded_by (user ID)
  - uploaded_date (timestamp)
  - description (what this evidence shows)
  - chain_of_custody (JSON array of access log)
  - created_at (timestamp)

TABLE: incident_actions
  - id (PRIMARY KEY)
  - incident_id (FK to incidents)
  - action_type (DisableAccount, ResetPassword, BlockIP, QuarantineEmail, etc.)
  - target (what was acted upon - user email, IP address, etc.)
  - status (Pending, InProgress, Completed, Failed, RolledBack)
  - executed_by (user ID)
  - executed_date (timestamp)
  - result (success/failure message)
  - api_response (JSON of API response for audit)
  - rollback_possible (boolean)
  - rollback_date (timestamp if rolled back)
  - created_at (timestamp)

TABLE: incident_communications
  - id (PRIMARY KEY)
  - incident_id (FK to incidents)
  - comm_type (InternalUpdate, CustomerNotification, RegulatoryReport, MediaStatement, etc.)
  - recipients (text field or JSON array)
  - subject (email subject or communication title)
  - body (communication content)
  - sent_by (user ID)
  - sent_date (timestamp)
  - approved_by (user ID, for external comms requiring approval)
  - approval_date (timestamp)
  - delivery_status (Sent, Failed, Pending)
  - created_at (timestamp)

TABLE: incident_lessons_learned
  - id (PRIMARY KEY)
  - incident_id (FK to incidents)
  - meeting_date (when lessons learned meeting held)
  - attendees (JSON array of user IDs)
  - what_went_well (text field)
  - what_could_improve (text field)
  - action_items (JSON array of actions with owner, due date, status)
  - created_by (user ID)
  - created_at (timestamp)
  - updated_at (timestamp)

TABLE: incident_reports
  - id (PRIMARY KEY)
  - incident_id (FK to incidents)
  - report_type (Executive, Final, Board, SOC2, Custom)
  - file_path (PDF storage path)
  - generated_by (user ID)
  - generated_date (timestamp)
  - approved_by (user ID)
  - approval_date (timestamp)
  - distributed_to (JSON array of recipients)
  - created_at (timestamp)

TABLE: oncall_schedule
  - id (PRIMARY KEY)
  - role (SecurityAnalyst, ITOperations, IRManager)
  - user_id (FK to users)
  - start_date (date)
  - end_date (date)
  - backup_user_id (FK to users)
  - active (boolean)
  - created_at (timestamp)

TABLE: incident_metrics
  - id (PRIMARY KEY)
  - metric_date (date - for aggregations)
  - total_incidents (count)
  - sev1_count (count)
  - sev2_count (count)
  - sev3_count (count)
  - sev4_count (count)
  - avg_mttd_minutes (average time to detect)
  - avg_mttr_minutes (average time to respond)
  - avg_recovery_hours (average recovery time)
  - user_reported_count (count)
  - automated_detected_count (count)
  - sla_compliance_percentage (decimal)
  - total_cost (decimal)
  - created_at (timestamp)

Integration with Existing Tables:
----------------------------------
- Link to existing 'users' table for authentication and user management
- Link to existing 'intune_device' table for device incidents
- Link to existing 'control' table for SOC2 control mapping
- Link to existing 'strikegraph_evidence' table to auto-file incident reports as evidence

RISK ASSESSMENT & MITIGATION
================================================================================

Technical Risks:
----------------
RISK: API rate limiting from Microsoft Graph
MITIGATION: Implement caching, batch requests, use webhooks instead of polling

RISK: Complex Azure permissions requiring tenant admin approval
MITIGATION: Document required permissions clearly, work with Azure admin early

RISK: Evidence storage growing large over time
MITIGATION: Implement retention policy (delete evidence after 2 years), use external storage for large files

RISK: Performance degradation with many concurrent incidents
MITIGATION: Database indexing, query optimization, consider PostgreSQL migration if needed

Process Risks:
--------------
RISK: IR Team not adopting new portal (continuing to use email/spreadsheets)
MITIGATION: Executive mandate, make portal easiest path, integrate with existing workflows

RISK: Incomplete playbooks causing confusion
MITIGATION: Pilot with IT team first, iterative improvement, allow custom playbooks

RISK: Regulatory notification templates becoming outdated
MITIGATION: Annual legal review, version control, require legal approval before sending

Security Risks:
---------------
RISK: Incident data contains sensitive information (credentials, PII)
MITIGATION: Role-based access control, audit logging, encryption at rest

RISK: API credentials with broad permissions
MITIGATION: Principle of least privilege, separate service accounts, key rotation

RISK: Evidence chain of custody broken
MITIGATION: Immutable logs, cryptographic signatures, access restrictions
