How generation behaves
  • The template is filled in place. Excel tables, dropdown validation against Masters, calculated columns (Auto_No, Importance, Risk) and the cross-sheet XLOOKUPs are preserved; table ranges are extended to match the new row counts.
  • FY25 carry-over columns are never written. ALAP's item guides mark a set of fields “No input required — from the FY25 register” (F04C: No, Required Protection Class, Information Category, Asset Manager, Viewing Authority, Media Format; F09A: ALAP Employee Number, Security Manager, PC Asset ID, issued equipment; and the equivalents on F06B and F08A). The generator preserves those exactly as supplied and leaves them blank on rows that had no FY25 record, rather than overwriting them with current Tracker values.
  • ISMS judgement calls are carried forward per row. Confidentiality / Integrity / Availability scores, threat and vulnerability classes, protect class and purpose text stay as filed. Only Tracker-owned fields (asset tag, hostname, owner, location, training dates, seat counts) are refreshed.
  • Only kit in service reaches F04C. An asset must have been seen within 180 days by at least one of: the RMM heartbeat, the UniFi client record, the Intune sync, or its AD last-logon. Assets with no signal from any of those are left off the sheet entirely — including template rows that match them, which would otherwise reappear mislabelled. F09-A endpoint rows are filtered to match, since column D is resolved against Supplement[Asset Name] and would read Not Found otherwise. Note this also drops live servers that run no agent and hold no AD/Intune/UniFi record.
  • Nothing else is deleted. Assets and workers the template lists that Tracker no longer has active are kept and stamped in Remarks as retired / departed, so the ledger keeps its history.
  • Dates are normalised. The template stores raw Excel serials (45512); generated rows write real dates formatted yyyy/mm/dd.
Gap: partner- and customer-provided system accounts

ALAP asks for every worker who uses a system provided by a customer or business partner to appear on F09A with their name and email, then on F09-A paired with that system and their account on it.

  • Covered. Every active employee is already on F09A with name and email. Microsoft 365 accounts are emitted on F09-A as BP_Name rows against the Microsoft partner row, with the UPN as the account ID and admin accounts marked Adminstrator.
  • Not covered. Accounts on the other partner platforms — GitLab, Cadence, Altium, Cliosoft, Arena/Omnify, Asana, QuickBooks — and on any customer-provided system (a Dell or Lenovo portal an engineer was told to use) are not recorded anywhere in Tracker, so the generator cannot emit them. Those rows have to be added by hand, or a register built so they generate like the rest.
ALAP template revisions applied at generation

ALAP issued a revision list against these ledgers. Each item is the same defect — row 6 is correct and rows 7+ were dragged out of step. They are applied every time the workbook is generated, so they hold for whichever template revision is uploaded and are a no-op on an already-corrected file.

  • Importance formula (F02B, F03A, F04C, F08A) — =MAX(L6:N[last row]) spans the whole table body instead of the row's own C/I/A triple, so one asset scored 4 drags every row above it to 4. Rewritten to =MAX(L6:N6) in the cells and in the table's stored calculated-column formula, which Excel otherwise re-broadcasts on open.
  • F02-A area selection — the “Area select” dropdown sits in column E on row 6 but column F from row 7 down, with the dependent lookup one column out to match. Rows 7+ are pulled back into line with row 6 and the stray column G lookup is removed.
  • F09-A / F09-B column A — row 6 validates against Name_Mail but rows 7+ against Worker_Name. Both sheets' XLOOKUPs key on Name (Mail), so the row-7+ rule rejected the only value that resolves. Now Name_Mail throughout.
